# Устройство сайта zolotoj-yasen.ru

Документ для того, кто пришёл на всё готовое: как это работает, где что лежит,
что делать, когда сломается, и как собрать заново, если пропадёт целиком.

Состояние на **20 августа 2026**. Все идентификаторы взяты из живого облака,
а не по памяти.

> **Что здесь НЕ лежит и никогда не должно.** Репозиторий публичный. Ключи,
> пароли и токены сюда не пишутся ни при каких обстоятельствах. Где они живут —
> в разделе «Секреты». Идентификаторы ресурсов ниже секретами не являются:
> без прав доступа они бесполезны.

## В одну строку

Статические файлы лежат в Яндекс Object Storage, раздаются через CDN Яндекса,
домен обслуживается Яндекс Cloud DNS, сертификат выпускает Certificate Manager,
выкладывает GitHub Actions. Сервера и базы нет.

## Путь посетителя

1. Браузер спрашивает `zolotoj-yasen.ru` у своего резолвера.
2. Резолвер идёт к `ns1/ns2.yandexcloud.net` — туда домен делегирован у reg.ru.
3. Зона отдаёт **ANAME** на цель CDN. ANAME нужен потому, что обычный CNAME
   в корне домена стандартом запрещён, а у reg.ru такой записи нет — это и была
   причина перенести DNS в Яндекс.
4. Браузер соединяется с узлом CDN по HTTPS. Сертификат — из Certificate Manager.
5. Узел CDN отдаёт файл из кэша (120 с) или идёт за ним в хранилище.
6. К хранилищу CDN обращается по **HTTP** и подставляет заголовок
   `Host: zolotoj-yasen.ru.website.yandexcloud.net`. Без явного заголовка
   хранилище не поймёт, какой бакет нужен.

Проверить любое звено:

```bash
# что отдают резолверы (dig в некоторых средах недоступен)
curl -s -H 'accept: application/dns-json' \
  'https://dns.adguard-dns.com/resolve?name=zolotoj-yasen.ru&type=A'

# хранилище напрямую, минуя CDN и домен
curl -sI http://zolotoj-yasen.ru.website.yandexcloud.net/

# делегирование глазами реестра .ru
whois zolotoj-yasen.ru | grep -i nserver
```

## Путь правки

1. Коммит в `main` (по SSH, см. «Доступ»).
2. GitHub Actions, сборка **«Deploy to GitHub Pages»**:
   - `rsync` собирает папку `_site`, выбрасывая служебное;
   - `aws s3 sync` заливает `_site` в бакет с ключом служебного аккаунта;
   - отдельный проход проставляет типы файлов;
   - та же папка уходит на GitHub Pages как запасная копия.
3. Через 1–2 минуты правка видна на сайте: столько живёт кэш узла CDN.
   Кнопки «сбросить кэш» нет — вместо неё короткий срок хранения.

**Почему типы файлов проставляются отдельно.** Хранилище само их не определяет:
`.css` уезжает как `text/plain`, и браузер такие стили не применяет — сайт
открывается голым текстом. Шаг `fix` в сборке убирать нельзя.

**Что не выкладывается:** `.git`, `.github`, `_site`, `tools`, `.claude`,
`content`, `*.py`, `*.md`, `.DS_Store`. Правило: всё, что кладётся в корень
репозитория, по умолчанию становится страницей сайта. Дважды на этом обжигались —
уезжали материалы рекламы с промокодом и настройки среды разработки.

## Яндекс Облако: что где настроено

Всё ниже делается через `yc`. Он ставится с
`curl -sSL https://storage.yandexcloud.net/yandexcloud-yc/install.sh | bash`
и живёт в `~/yandex-cloud/bin/yc`. Полезно:
`export YC_CLI_INITIALIZATION_SILENCE=true`.

### Object Storage

Бакет `zolotoj-yasen.ru`. **Имя обязано совпадать с доменом** — иначе
не работает раздача сайта по своему домену.

- анонимный доступ: чтение — да, список файлов — нет;
- включён режим сайта: `index.html` как индекс каталога, `404.html` как ошибка.

CLI настройки сайта не показывает, поэтому проверяют поведением:

```bash
curl -s -o /dev/null -w '%{http_code}\n' http://zolotoj-yasen.ru.website.yandexcloud.net/sobytiya/   # 200
curl -s http://zolotoj-yasen.ru.website.yandexcloud.net/net-takogo/ | grep -c 'Золотой Ясень'        # 1
```

Задать заново:

```bash
yc storage bucket update --name zolotoj-yasen.ru \
  --website-settings '{"index":"index.html","error":"404.html"}'
```

### CDN

Ресурс `bc8rscsoctj24nzj4dym`, имена `zolotoj-yasen.ru` и `www.zolotoj-yasen.ru`.

- источник — группа `yasna-bucket` → `zolotoj-yasen.ru.website.yandexcloud.net`, протокол HTTP;
- заголовок Host к источнику задан явно;
- кэш: 120 с на узле, 60 с в браузере;
- HTTP уводится на HTTPS;
- сертификат — из Certificate Manager.

```bash
yc cdn resource get bc8rscsoctj24nzj4dym
```

**Важно:** менять ресурс, когда включено перенаправление на HTTPS, а сертификат
не привязан, нельзя — API отказывает и ресурс залипает в неизменяемом состоянии.
Порядок: сперва сертификат, потом перенаправление.

### Certificate Manager

Сертификат `yasna-site` (`fpqnvtj2cj91mkar4bsr`), Let's Encrypt, тип MANAGED —
продлевается сам. Подтверждение владения — через записи `_acme-challenge`
в зоне DNS; **пока они там лежат, продление работает.** Удалять их нельзя.

```bash
yc certificate-manager certificate get --name yasna-site
```

### Cloud DNS

Зона `yasna` (`dns7nisn9onl1md24p3f`), публичная, обслуживает `zolotoj-yasen.ru.`

| Запись | TTL | Тип | Значение |
|---|---|---|---|
| `zolotoj-yasen.ru.` | 300 | ANAME | `bdd676f8d5e77253.topology.gslb.yccdn.ru.` |
| `www.zolotoj-yasen.ru.` | 300 | CNAME | то же |
| `_acme-challenge.zolotoj-yasen.ru.` | 600 | CNAME | `fpqnvtj2cj91mkar4bsr.cm.yandexcloud.net.` |
| `_acme-challenge.www.zolotoj-yasen.ru.` | 600 | CNAME | то же |

```bash
yc dns zone list-records --name yasna
```

Ни MX, ни TXT в зоне нет: почты на домене нет, подтверждения Вебмастера
и Google сделаны файлами в корне сайта, а не записями DNS.

### Служебный аккаунт

`yasna-deploy` (`ajea64l3ckas554hakei`), единственная роль — `storage.editor`
на каталоге. Он может писать в хранилище и больше ничего: ни доменов,
ни CDN, ни счетов не касается.

```bash
yc resource-manager folder list-access-bindings b1gc964j4lm3jfp3h038
```

## Наблюдение

`tools/monitor/proverka.py`, запускается сборкой «Сайт недоступен?».

Три замера: прямой запрос главной, доступность **с узлов в России**
(через check-host.net) и срок сертификата.

Тревога — письмо владельцу репозитория — поднимается, если:

- главная не открылась или отдала не то;
- молчат **все** российские узлы;
- молчит больше половины узлов мира;
- сертификату осталось меньше 14 дней;
- **российский замер не удалось сделать вовсе** после трёх попыток.

Последний пункт важнее, чем кажется: монитор, который не может проверить
главное и при этом рапортует «всё в порядке», опаснее отсутствующего.

Порог «вся Россия» выбран по наблюдениям: в спокойный день отвечают 36–39
узлов из 40, единичные таймауты — норма, и письма по ним превратятся в шум.

## Аварийные сценарии

| Симптом | Что проверить | Что делать |
|---|---|---|
| Сайт не открывается ниоткуда | хранилище напрямую по адресу `…website.yandexcloud.net` | если хранилище живо — беда в CDN или DNS; если нет — смотреть бакет |
| Не открывается только из России | замер с российских узлов | вернуть домен на GitHub Pages (ниже) |
| Предупреждение о сертификате | `yc certificate-manager certificate get --name yasna-site` | проверить, что записи `_acme-challenge` на месте; при `INVALID` заказать заново |
| Сайт открывается голым текстом | тип файла `.css` | шаг `fix` в сборке не отработал — перезалить с явным типом |
| Выкладка падает | вкладка Actions | чаще всего протух ключ служебного аккаунта: создать новый и обновить секреты |
| Правка не появилась | прошло меньше 2 минут? | кэш узла CDN живёт 120 с |

### Аварийный возврат на GitHub Pages

Нужен, если облако недоступно целиком. Пока DNS живёт в Яндексе, вернуться
можно правкой зоны; если недоступна и она — менять делегирование у reg.ru
обратно на `ns1.reg.ru` / `ns2.reg.ru`.

```bash
# вариант 1: облако живо, меняем только записи
yc dns zone replace-records --name yasna \
  --record "zolotoj-yasen.ru. 300 A 185.199.108.153" \
  --record "zolotoj-yasen.ru. 300 A 185.199.109.153" \
  --record "zolotoj-yasen.ru. 300 A 185.199.110.153" \
  --record "zolotoj-yasen.ru. 300 A 185.199.111.153" \
  --record "www.zolotoj-yasen.ru. 300 CNAME avvacumrechevoi.github.io."
yc dns zone delete-records --name yasna \
  --record "zolotoj-yasen.ru. 300 ANAME bdd676f8d5e77253.topology.gslb.yccdn.ru."
```

Расходится за 5 минут (TTL 300). Копия сайта на Pages всегда свежая —
её обновляет та же сборка.

**Вариант 2** — облако недоступно: в панели reg.ru у домена сменить
серверы имён на `ns1.reg.ru` / `ns2.reg.ru` и убедиться, что в зоне reg.ru
лежат четыре адреса GitHub Pages. Расходится дольше — до суток.

## Восстановление с нуля

Если пропало всё, кроме репозитория. Порядок важен.

```bash
export YC_CLI_INITIALIZATION_SILENCE=true

# 1. бакет с именем, равным домену
yc storage bucket create --name zolotoj-yasen.ru \
  --public-read --public-list=false --public-config-read
yc storage bucket update --name zolotoj-yasen.ru \
  --website-settings '{"index":"index.html","error":"404.html"}'

# 2. залить сайт (типы файлов — обязательно явно, см. выше)
#    проще всего: запустить сборку в GitHub Actions

# 3. источник и ресурс CDN — БЕЗ перенаправления на HTTPS
yc cdn origin-group create --name yasna-bucket \
  --origin source=zolotoj-yasen.ru.website.yandexcloud.net,enabled=true
yc cdn resource create --cname zolotoj-yasen.ru \
  --secondary-hostnames www.zolotoj-yasen.ru \
  --origin-group-id <id группы> --origin-protocol http --active=true \
  --dont-use-ssl-cert --host-header zolotoj-yasen.ru.website.yandexcloud.net \
  --gzip-on --cache-expiration-time-default 120 --browser-cache-expiration-time 60

# 4. зона DNS и записи подтверждения
yc dns zone create --name yasna --zone zolotoj-yasen.ru. --public-visibility

# 5. сертификат: даст CNAME-подтверждения, положить их в зону
yc certificate-manager certificate request --name yasna-site \
  --domains zolotoj-yasen.ru,www.zolotoj-yasen.ru --challenge dns

# 6. дождаться ISSUED, привязать к CDN и включить перенаправление
yc cdn resource update <id ресурса> \
  --cert-manager-ssl-cert-id <id сертификата> --redirect-http-to-https

# 7. ТОЛЬКО ПОСЛЕ проверки снаружи — направить домен на CDN
```

**Шаг 7 нельзя торопить.** Сертификат расходится по узлам CDN десятками минут:
сразу после привязки TCP доходит, а шифрованное соединение сбрасывается
(«Connection reset by peer»). Переключение домена в этот момент кладёт сайт.
Проверять — снаружи, например через check-host.net, и лучше сперва перевести
на CDN только `www` как пробную площадку.

## Грабли, проверенные на себе

**Из рабочей среды разработчика проверять CDN нельзя.** Она ходит через прокси,
который разрешает имя сам и игнорирует подмену адреса и заголовка `Host`.
Проверка «CDN отдаёт 200» на деле измеряла GitHub Pages. Отличить по ответу
невозможно: сертификат у обоих от Let's Encrypt и на то же имя. Мерить только
снаружи.

**Сертификат на узлах CDN появляется не сразу** — от четверти часа до часа.

**Хранилище не проставляет типы файлов.** `.css` и `.js` → `text/plain`,
`.svg` → `text/xml`.

**ANAME в корне работает, CNAME — нет.** Стандарт запрещает CNAME в корне зоны.

**Смена серверов имён расходится до суток.** Чтобы это прошло незаметно,
новая зона сначала повторяла прежние записи один в один: какой бы резолвер
ни ответил, ответ одинаковый. На CDN переключались отдельным шагом.

**check-host.net без заголовка `User-Agent` отвечает отказом** — и замер
молча пропускается.

## Что осознанно не сделано

- **Нет сервера.** Живой счётчик мест, личный кабинет и автоматические
  напоминания требуют бэкенда, который на восьмидесяти местах не окупает
  поддержки.
- **Нет фреймворка.** Переезд на другой хостинг занял день именно потому,
  что сайт — набор файлов.
- **Нет сброса кэша по кнопке.** Требует ключа с более широкими правами;
  вместо него короткий срок хранения.
- **Вторая фаза афиши не подключена** — источником служит файл, а не общая
  таблица руководителей. Разборщик написан и проверен, нужна публичная
  ссылка на файл.
